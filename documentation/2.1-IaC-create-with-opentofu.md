## Fresh create using Opentofu
After completing import of resources, I am still curious of the process to create a fresh server using IaC. 

1. Write an aws_instance with the same AMI, instance type, and key pair, but without the import block. 

*(Without using console,I have zero idea what field should be populated even with the guide of the documentation. So I referenced the plan output during the import phase as a guideline.)*

2. Rerun `tofu validate` until there are no conflict and the configuration is valid.

3. This task has shown alot of insights as to which field are mainly required for the creation of the resource. The AWS computed 

4. There are fields/blocks with value `(known after apply)` seen in the plan output. The possible cases are: 
- AWS computed fields (or the Attribute Reference group in the [documentation](https://search.opentofu.org/provider/hashicorp/aws/latest/docs/resources/instance#attribute-reference))
- Computed and optional. Meaning if no value is assgined to these fields, AWS will compute it
- Referenced from another resource. This is where `outputs.tf` come into play and how dependencies work in Opentofu.

I also got to know that AMI IDs are region-unique. Meaning using the same AMI but in a another region (eg. `us-east-1`), it will referenced to another image. 

```bash
aws ssm get-parameter --name "/aws/service/canonical/ubuntu/server/26.04/stable/current/amd64/hvm/ebs-gp3/ami-id" --region us-east-1 --query "Parameter.Value" --output text
ami-080341f184b848d0b
```
```bash
aws ssm get-parameter --name "/aws/service/canonical/ubuntu/server/26.04/stable/current/amd64/hvm/ebs-gp3/ami-id" --region eu-central-1 --query "Parameter.Value" --output text
ami-0dbce11a00a38ace4
```

I notice the AMI value still differ, after some research, The SSM parameter always points to Canonical's latest Ubuntu 26.04 build. The AMI selectef in the console was an earlier build of the same release. Canonical publishes new AMI builds regularly, mostly for patches, so one release can have several IDs in the same region.

```bash
aws ec2 describe-images --image-ids ami-0303e2e4a29f041a3 ami-0dbce11a00a38ace4 --region eu-central-1 --query "Images[].[ImageId,Name,CreationDate]" --output text

ami-0dbce11a00a38ace4   ubuntu/images/hvm-ssd-gp3/ubuntu-resolute-26.04-amd64-server-20261003   2026-10-03T06:35:46.000Z
ami-0303e2e4a29f041a3   ubuntu/images/hvm-ssd-gp3/ubuntu-resolute-26.04-amd64-server-20260604   2026-06-04T06:47:15.000Z
```

This reveals  a maintenance concern. Production setups usually handle it with one of two patterns:

- Pin the AMI and update it deliberately, as a planned replacement.
- Look up the latest AMI and tell OpenTofu to ignore changes to that field with a lifecycle block, so routine AMI updates don't trigger a replacement.
