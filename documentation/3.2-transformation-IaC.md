## Preparation: describing the existing server in code

Most of Project 1 was done by hand: the `dev` and `ansible` accounts, their keys, the sshd settings, UFW, the hostname. None of it was in Ansible, so the server could not be rebuilt and a second server could not be set up the same way. The bastion is a second server, so the existing roles in Ansible first have to describe what was done by hand. `ssh` takes the users, keys and sshd settings. `base` takes the machine-wide settings.

Each change below was run against the existing server and should report `ok` with `changed=0`. That result means the code matches what was built by hand, the same idea as a clean `tofu plan` after an import.

### 1. `ssh` role manages a list of users

The Ansible role used to take one user and one key through `-e` on the command line. A plain run of `setup.yml` would then create an account from the default value and fail on the placeholder key. It now loops over a list.

`group_vars/myhosts/vars.yml` holds the real list. Public keys are not secret, so they do not need the vault:

```yaml
ssh_users:
  - name: dev
    key: "ssh-ed25519 AAAA... devops-playground"
  - name: ansible
    key: "ssh-ed25519 AAAA... ansible-key"
```

`roles/ssh/defaults/main.yml` sets `ssh_users: []`, so on a host with no list the role does nothing. The two servers get the real list from `group_vars/myhosts/vars.yml`, which overrides the default. It matters when the role runs on a host that has no list. For example, a new server you add later in a group outside `myhosts`, or the day the vars file is renamed or mistyped. Without the default, the role crashes. 

`roles/ssh/tasks/main.yml`:

```yaml
- name: Ensure target user account exists
  ansible.builtin.user:
    name: "{{ item.name }}"
    state: present
    shell: /bin/bash
  loop: "{{ ssh_users }}"

- name: Add authorized key for target user
  ansible.posix.authorized_key:
    user: "{{ item.name }}"
    state: present
    key: "{{ item.key }}"
  loop: "{{ ssh_users }}"
```

**Note: `loop` belongs to the task, not the module.** It lines up with the task's `name:` and with `ansible.builtin.user:`. Anything indented under the module name is passed to the module. Anything at the task's own level (`name`, `loop`, `notify`, `tags`) tells Ansible how to run the task.

```bash
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags ssh
# ok=3: Gathering Facts plus the two tasks, each covering dev and ansible
```

### 2. sudo membership

In Project 1 both accounts were added to the `sudo` group with `usermod -aG sudo`. Added to the `user` module in the first task:

```yaml
    groups: sudo
    append: true
```

Without `append: true`, `groups` means "these are the only extra groups", and Ansible would remove `dev` from the `users` group it already belongs to. With it, `sudo` is added and the rest is left alone, like the `-a` in `usermod -aG`.

Result: `ok=3`, `changed=0`. Both accounts were already in the group.

### 3. sshd settings

In Project 1 the settings were edited by hand in `/etc/ssh/sshd_config`. The role does not touch that file. It writes one small file of its own into the folder `/etc/ssh/sshd_config.d/`.

**Why not edit the main file again.** Editing by hand was the direct way to learn the settings in Project 1. For automation, a separate file is better:

- Ansible needs to know nothing about the main file, whose contents differ between Ubuntu releases. One `copy` task writes the whole file.
- The main file stays as Ubuntu ships it, so `apt upgrade` never stops to ask about a "locally modified" config.
- Undoing it means deleting one file.

The folder is the place Ubuntu provides for local changes. The app server has both the old hand edit and the new file, saying the same thing. The bastion has only the file.

**How the folder works.** Three facts together explain why a file in that folder takes priority over the main config:

1. The main file pulls in the folder. Near the top of `/etc/ssh/sshd_config` there is this line, which tells sshd to read every `.conf` file in the folder as if its contents were written at that point:
   ```
   Include /etc/ssh/sshd_config.d/*.conf
   ```
   Check it with `grep -n Include /etc/ssh/sshd_config`.
2. sshd reads from top to bottom. Because the `Include` line is near the top, the files in the folder are read before the rest of the main file.
3. For each setting, sshd keeps the first value it meets and ignores later ones. This is the opposite of many programs, where the last value wins.

The reading order on this server is therefore:

```
/etc/ssh/sshd_config            (top of file)
  -> Include: 10-hardening.conf     PermitRootLogin no    <- read first, kept
  -> Include: other .conf files in the folder, in alphabetical order
/etc/ssh/sshd_config            (rest of file)
     PermitRootLogin no             <- the Project 1 edit, read later, ignored
```

Both places say the same thing here, so behaviour did not change. If they ever disagreed, the file in the folder would win.

**Two limits to know:**

- The `Include` line is there by default on Ubuntu and Debian. It is not part of OpenSSH itself, so older releases and some other distributions do not have it. Without the line, sshd never reads the folder and the file is ignored without any error.
- Files in the folder are read in alphabetical order. The `10-` prefix puts this file ahead of files with higher numbers, such as the `60-cloudimg-settings.conf` that ships in the Ubuntu cloud image. A file with a lower name, such as `00-something.conf`, would be read first and would win for any setting it contains.

Because of both limits, `sudo sshd -T` is the check in the server that counts. It prints the settings sshd is really using, whichever file they came from. (Run `sudo man sshd` to learn more. )

Third task in `roles/ssh/tasks/main.yml`:

```yaml
- name: Disable root login and password authentication
  ansible.builtin.copy:
    dest: /etc/ssh/sshd_config.d/10-hardening.conf
    owner: root
    group: root
    mode: '0644'
    validate: /usr/sbin/sshd -t -f %s
    content: |
      PermitRootLogin no
      PasswordAuthentication no
      PubkeyAuthentication yes
  notify: Restart ssh
```

`roles/ssh/handlers/main.yml`:

```yaml
- name: Restart ssh
  systemd:
    name: ssh
    state: restarted
```

**Why `copy` and not `lineinfile`:** `lineinfile` changes one line inside an existing file and leaves the rest as it finds it, so it would take one task per setting in a file Ansible otherwise knows nothing about. `copy` writes a whole file, so Ansible owns this one completely and the main `sshd_config` stays as Ubuntu ships it. A server set up this way does not get the "locally modified configuration file" prompt that `apt upgrade` showed in Project 1.

**How `validate` works:** Ansible writes the new content to a temporary file on the server and runs the command with `%s` replaced by that path. `sshd -t` tests a config without starting anything, and `-f` says which file. If the test passes, the temporary file is moved into place. If it fails, the task fails and the destination is never touched.

`%s` is a fixed placeholder defined by AnsibleAnsible refuses a `validate` command that does not contain it. At run time it becomes the temporary file's path, so the server runs something like `/usr/sbin/sshd -t -f /tmp/ansible.abc123`.

**Mistakes in my first draft:**
- `enabled: yes` in the handler. A handler should only restart. On this server `ssh.service` is not enabled on purpose, because Ubuntu starts it through `ssh.socket`.

The mode `0644` applies to the file, which only needs to be readable. The folder already exists and `copy` does not change its permissions.

A second SSH session as `dev` was kept open as a fallback during the run.

```bash
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags ssh
# First run:  ok=5, changed=2 (the file was created, the handler restarted ssh)
# Second run: ok=4, changed=0
```

This is the one step where `changed` was expected on the first run, because the file did not exist yet. The settings in effect are the same as before:

```bash
sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication'
# permitrootlogin no
# pubkeyauthentication yes
# passwordauthentication no
```

The `ssh` role now describes everything Project 1 did for users and SSH: the accounts, their keys, sudo membership and the sshd settings.

### 4. UFW in the `base` role

In Project 1 the firewall was set up with `sudo ufw allow ssh` and then `sudo ufw enable`. Added to `roles/base/tasks/main.yml` with the `community.general.ufw` module:

```yaml
- name: Allow ssh
  community.general.ufw:
    rule: allow
    port: '22'
    proto: tcp

- name: Enable Firewall
  community.general.ufw:
    state: enabled
    policy: deny
    direction: incoming
```

**The order matters.** On a fresh server, enabling the firewall before the SSH rule exists would cut off the connection Ansible is using.

**Why the policy is stated.** UFW denies incoming traffic by default, so the two extra lines change nothing on this server. They are there because "allow 22, then enable" only protects the server thanks to that default, and the role should not depend on something it does not mention.

UFW is the one setting in this role that can lock me out, so the change was checked in three steps:

```bash
# 1. Record the current state on the server
sudo ufw status verbose

# 2. Dry run. --check makes no changes, --diff shows what would change
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags base --check --diff
# ok=8, changed=1

# 3. Real run, with a second SSH session open as a fallback
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags base
```

The one `changed` is the apt cache refresh, which reports `changed` on every run. Both UFW tasks were `ok`, and `sudo ufw status verbose` was the same before and after.

For now the rule allows SSH from anywhere, matching the server today. Once the bastion exists, the allowed source becomes a variable so this server accepts SSH from the bastion only.

### 5. fail2ban jail in the `base` role

In Project 1 `/etc/fail2ban/jail.local` was written by hand. Added between "Install fail2ban" and "Start and enable fail2ban", so on a fresh server the file is in place before the service first starts:

```yaml
- name: Configure fail2ban configuration
  ansible.builtin.copy:
    dest: /etc/fail2ban/jail.local
    owner: root
    group: root
    mode: '0644'
    content: |
      [sshd]
      enabled = true
      port = ssh
      maxretry = 3
      bantime = 3600
      findtime = 600
  notify: Restart fail2ban
```

`roles/base/handlers/main.yml`:

```yaml
- name: Restart fail2ban
  ansible.builtin.systemd:
    name: "{{ fail2ban_service }}"
    state: restarted
    enabled: true
```

`copy` is enough for six fixed lines. `content` also accepts variables, so a value could later differ per server without switching to `template`. There is no `validate` here, because fail2ban has no single-file syntax check like `sshd -t`.

The content was copied from the file on the server so the two match byte for byte:

```bash
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags base --check --diff
# ok=9, changed=1 (apt cache only, the jail task was ok)

sudo fail2ban-client status sshd
# The sshd jail is still listed
```

### 6. Remaining machine-wide settings in the `base` role

Four settings from Project 1 were left: timezone, hostname, the `/etc/hosts` lines and automatic security updates. None of them can lock me out, so they were added together.

The server's current values were checked first, so I knew what the role had to match:

```bash
timedatectl | grep "Time zone"            # Europe/Berlin
hostname                                  # devops-playground-server
cat /etc/hosts                            # 127.0.0.1 localhost / 127.0.1.1 devops-playground-server
cat /etc/apt/apt.conf.d/20auto-upgrades   # the two APT::Periodic lines
```

Two variables are involved:

- `timezone: "Europe/Berlin"` in `roles/base/defaults/main.yml`. It is the same for every server unless overridden.
- `server_hostname`, set per host on the host's line in `inventory.ini`, because every server has a different one:
  ```
  my_host_01 ansible_host=<server-ip> ansible_user=ansible server_hostname=devops-playground-server
  ```

`unattended-upgrades` was added to the package list in "Install useful utilities". New tasks in `roles/base/tasks/main.yml`:

```yaml
- name: Set timezone
  community.general.timezone:
    name: "{{ timezone }}"

- name: Set hostname
  ansible.builtin.hostname:
    name: "{{ server_hostname }}"

- name: Set hostname in /etc/hosts
  ansible.builtin.lineinfile:
    path: /etc/hosts
    regexp: '^127\.0\.1\.1'
    line: '127.0.1.1 {{ server_hostname }}'

- name: Set localhost
  ansible.builtin.lineinfile:
    path: /etc/hosts
    regexp: '^127\.0\.0\.1'
    line: "127.0.0.1 localhost"

- name: Configure unattended-upgrades configuration
  ansible.builtin.copy:
    dest: /etc/apt/apt.conf.d/20auto-upgrades
    owner: root
    group: root
    mode: '0644'
    content: |
      APT::Periodic::Update-Package-Lists "1";
      APT::Periodic::Unattended-Upgrade "1";
```

The `20auto-upgrades` file is what `dpkg-reconfigure unattended-upgrades` wrote in Project 1 when I answered "Yes".

**Why `lineinfile` for `/etc/hosts`, after choosing `copy` for sshd.** `/etc/hosts` belongs to the system and has other lines that the role should leave alone. Only two lines matter here. `regexp` finds the line to look at (`^` means start of line, and the backslashes make each dot a literal dot), and `line` is what that line must say. It adds the line if no line starting with that address is found.

```bash
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags base
# ok=14, changed=1 (apt cache only)
```

The `base` and `ssh` roles now describe everything that was done by hand in Project 1.

## Incident: locked out by my own fail2ban

On 10 October, SSH to the server suddenly failed with `Connection refused` for every account. The instance was running, the public address had not changed, the console log showed a healthy boot, and a reboot did not help. About an hour later it worked again without any fix.

The cause turned up while adding the fail2ban jail to the `base` role. `sudo fail2ban-client status sshd` showed `Total banned: 1`, and the security group only lets my own address reach port 22, so the banned address had to be mine. The fail2ban log confirmed it:

```bash
sudo grep -E "Ban|Unban" /var/log/fail2ban.log.1
# 16:47:30  [sshd] Ban <my-ip>
# 17:45:03  [sshd] Unban <my-ip>          <- fail2ban stopping for the reboot
# 17:45:23  [sshd] Restore Ban <my-ip>    <- ban put back after the reboot
# 17:47:29  [sshd] Unban <my-ip>          <- one hour after the ban
```

Just before 16:47 I had several failed logins in a row while testing the `ssh` role (logging in as a user that did not exist yet). That reached `maxretry = 3` within `findtime = 600` seconds, and the jail blocked my address for `bantime = 3600` seconds.

What I learned:

- fail2ban blocks by rejecting the connection, which the SSH client reports as `Connection refused`. A security group block looks different: the connection hangs and times out.
- A reboot does not clear a ban. fail2ban saves active bans and restores them when it starts.
- The jail does not know who is failing. Three wrong attempts from the right person count the same as three from an attacker.
- `sudo fail2ban-client set sshd unbanip <address>` lifts a ban, but it needs a way into the server, which is the thing that is blocked. Without one, the only option is to wait out `bantime`.
- When `grep` found nothing at first, the reasons were that the log lines say `Ban` with a capital letter, and that the day's entries had been rotated into `fail2ban.log.1`.

### Fix: never ban the admin address

fail2ban's `ignoreip` setting lists addresses it will never ban. Failed logins from those addresses are not counted, so they can never reach `maxretry`.

My home address should not be in a public repo, so the role carries a harmless default and the real value lives in the vault.

`roles/base/defaults/main.yml`, the fallback, which is only the server's own loopback addresses:

```yaml
fail2ban_ignoreip: "127.0.0.1/8 ::1"
```

One line added to the jail content in `roles/base/tasks/main.yml`:

```yaml
      findtime = 600
      ignoreip = {{ fail2ban_ignoreip }}
  notify: Restart fail2ban
```

The real value, added to the encrypted file with `EDITOR=nano ansible-vault edit group_vars/myhosts/vault.yml`. The command decrypts, opens the editor and encrypts again on save, so the file is never left in plain text:

```yaml
fail2ban_ignoreip: "127.0.0.1/8 ::1 <my-ip>"
```

How the value reaches fail2ban:

1. Ansible collects the variables for the host. Values in `group_vars` win over role defaults, so the vault's value is used.
2. `{{ fail2ban_ignoreip }}` in the task is replaced by that value.
3. The file is written to the server. It differs by one line, so the task reports `changed`.
4. The handler restarts fail2ban, which reads the new setting.

**Notes:**
- The default has to be in `defaults/`, not `vars/`. `group_vars` can override `defaults/` but not `vars/`.
- `ignoreip` is a list separated by spaces on one line. Entries can be single addresses or ranges such as `172.31.0.0/16`.
- Every line of a `content: |` block must keep the same indentation. I first added the new line two spaces short, and YAML read it as a module setting and failed with `could not find expected ':'`.
- My home address can change. When it does, the security group rule and this value both need updating.

```bash
ansible-playbook -i inventory.ini setup.yml --ask-vault-pass --tags base
# ok=10, changed=3 (apt cache, the jail file, the handler)

sudo fail2ban-client get sshd ignoreip
# |- 127.0.0.0/8
# |- ::1
# `- <my-ip>
```

This matters for the bastion. Once all SSH to this server arrives from the bastion, three failed logins by anyone would ban the bastion's address and lock out every admin for an hour. When the bastion exists, this server's `ignoreip` becomes the bastion's private address, and my own address moves to the bastion's jail.

## Infrastructure in code (`iac/`)

Everything here is one OpenTofu configuration in `iac/`, split into files (`main.tf`, `security.tf`, `variables.tf`, `outputs.tf`). OpenTofu reads every `.tf` file in a folder as one configuration, so the split is only for readability. I did not split into separate folders, because each folder would have its own state and the bastion rule needs to refer to both security groups. Modules were not worth it yet either: they pay off when the same pattern is built more than once, and they should be cut by purpose (for example "bastion"), not by resource type.

### 1. Completing the existing instance

After the import in Project 2, `main.tf` declared only the AMI, instance type and name. The other attributes were not missing from OpenTofu's view: the import read them from AWS into the state file, and OpenTofu does not compare optional settings that are left out of the config, so the plan was clean. But those values came from my choices in the console launch wizard, not from AWS defaults. A server rebuilt from that config would have had no key pair, the VPC's default security group and an arbitrary default subnet.

Added to the instance:

```hcl
  key_name               = "devops-playground"
  subnet_id              = "subnet-09b78eb100211a9ef"
  vpc_security_group_ids = [aws_security_group.this.id]
  lifecycle {
    prevent_destroy = true
  }
```

`prevent_destroy` makes OpenTofu refuse any plan that would destroy or replace this instance. It is there because this server was built by hand. It does not protect against deleting the instance in the AWS console, and it disappears if the whole resource block is removed. `tofu plan` reported no changes.

### 2. Importing the security group and its rules

The launch wizard had created a security group called `launch-wizard-1`. Bringing it into OpenTofu is what allows the bastion rule to be added in code.

```bash
aws ec2 describe-security-groups --group-ids <sg-id> --query "SecurityGroups[0].[GroupName,Description,VpcId]" --output table
aws ec2 describe-security-group-rules --filters Name=group-id,Values=<sg-id> --query "SecurityGroupRules[].[SecurityGroupRuleId,IsEgress,IpProtocol,FromPort,ToPort,CidrIpv4]" --output table
```

Three resources in `security.tf`, each with an `import` block: the group, its inbound SSH rule and its outbound rule. Each rule is its own resource so that one can be added or removed without touching the others.

**Notes:**
- The group's `name` and `description` must be copied exactly. Changing either forces AWS to replace the group.
- The outbound rule has protocol `-1`, meaning all protocols, so it takes no ports.
- My home address is not in the repo. The rule uses `var.admin_cidr`, and the value is in `terraform.tfvars`, which `.gitignore` excludes.
- `admin_cidr` has no default. My first version had `default = "0.0.0.0/0"`, which would have opened SSH to the whole internet whenever the tfvars file was missing. With no default, OpenTofu stops and asks.

```bash
tofu plan    # 3 to import, 0 to add, 0 to change, 0 to destroy
tofu apply
tofu plan    # No changes
```

## Architecture at the end of this phase

The network picture is the same as at the end of Project 3: one server, one way in. What changed is how completely the server is described in code.

```
iac/       OpenTofu
             the instance: AMI, type, key pair, subnet, security group
             the security group and both its rules (imported)
             my address in terraform.tfvars, outside the repo
ansible/   Ansible
             base: updates, UFW, fail2ban jail (ignoring my address), timezone,
                   hostname, /etc/hosts lines, unattended-upgrades
             ssh:  users dev and ansible, their keys, sudo, the sshd file
             nginx + app: the static site
```

| Perspective | At this point |
|---|---|
| Visitor | Nothing is public. |
| Developer | Unchanged: the static site in the `app` role. |
| Admin | Unchanged paths. New: everything Project 1 did by hand is now in the roles, so a second server can be set up the same way. That is the precondition for the bastion. |
