# Incident: Ansible "Timeout waiting for privilege escalation prompt"

**STATUS: RESOLVED.** Root cause was `sudo-rs` (Ubuntu 26.04's new default, Rust
rewrite of `sudo`) wrapping Ansible's custom `-p` prompt instead of replacing it
(see "Resolution" section at the bottom). The Python 3.14 controller theory in
this doc's earlier sections was the wrong mechanism, kept here for the record
of how the investigation actually unfolded.

## Symptom

Any Ansible command using privilege escalation (`-b` / `become: true`) fails after
exactly the configured timeout window (12s default), regardless of the task:

```
ansible myhosts -i inventory.ini -b -m command -a "whoami" --ask-vault-pass
```

```
[ERROR]: Task failed: Timeout (12s) waiting for privilege escalation prompt:
my_host_01 | UNREACHABLE! => {
    "changed": false,
    "msg": "Task failed: Timeout (12s) waiting for privilege escalation prompt:",
    "unreachable": true
}
```

Plain connectivity (`ansible ... -m ping`, no `become`) works correctly and
instantly. Only privilege escalation is affected.

## Environment

- Control node: WSL (Ubuntu `resolute`), `ansible-core 2.20.1`, apt-installed
- Control node Python: `3.14.4` (only Python available on this OS release — no
  `3.12`/`3.13` package in default repos)
- Managed node: EC2 instance, same Ubuntu `resolute` release, Python `3.14.4`
- Auth: dedicated `ansible` automation user, SSH key loaded in `ssh-agent`,
  passwordless login, password-protected sudo (`ansible_become_password` stored
  in `group_vars/myhosts/vault.yml`, encrypted with Ansible Vault)

**Note on what "pipelining" means (hypothesis #8):** by default, Ansible delivers a module's code to the remote host in several separate steps.
- writes a Python script to a temporary file
- uploads that file to the server over the connection
- executes it as its own command
- then deletes it afterward

With `pipelining = True` in `ansible.cfg`, this changes. Ansible instead streams the script's content directly via stdin to a bare Python interpreter invocation on the remote side, so no temp file is ever written to disk. This removes several round trips per task and can meaningfully speed up execution, particularly over a high-latency connection. It is not the default, since it requires the remote sudoers configuration to not have `requiretty` set, something Ansible cannot assume is true for every environment.

**What `requiretty` means:** a `sudo` configuration setting (`Defaults requiretty` in `/etc/sudoers`) that forces `sudo` to refuse running unless invoked from a genuine interactive terminal, making it harder for a malicious script, cron job, or background process to silently invoke `sudo` without a person actually at a keyboard. It matters for pipelining because streaming a script via stdin changes the way the remote command gets invoked, in a way that can conflict with a tty requirement. If `requiretty` is on, `sudo` can refuse to run at all under that kind of invocation, breaking privilege escalation combined with pipelining entirely. Pipelining's compatibility therefore quietly depends on `requiretty` being off, which it is by default on modern Ubuntu, but Ansible has no way to verify that holds true for every environment it might run against.

## Conclusion so far

Every remote-side component — `sudo`'s custom prompt, the password-via-stdin
mechanism, the success-marker echo, the Python interpreter startup, the full
nested shell/quoting structure Ansible generates — has been reproduced manually
and is **consistently sub-second**. Nothing on the server side is slow or broken.

The delay is therefore isolated to the **local controller process**: `ansible-core
2.20.1` running under `Python 3.14.4` on WSL. Python 3.14 is extremely new (this
Ubuntu release ships nothing else), and `ansible-core`'s connection plugin relies
on lower-level Python mechanisms (`select`/`poll`, subprocess pipe reads) to detect
the remote prompt in real time. The working theory is a timing/compatibility issue
between `ansible-core` and this specific, very new controller Python version —
not yet validated against it.

## Resolution (by Codex)

**Root cause:** Ubuntu 26.04 ("resolute") ships `sudo-rs` (a Rust rewrite of
`sudo`) as the default `/usr/bin/sudo`. `sudo-rs` does not fully replicate
traditional `sudo` behavior: when given a custom prompt via `-p`, it *wraps*
the supplied string instead of replacing the prompt outright. Ansible's sudo
become plugin generates a unique prompt (`-p "[sudo via ansible, key=<random>]
password:"`) and scans remote output for that *exact* string to know when to
send the become password. `sudo-rs` instead emits:

```
[sudo: [sudo via ansible, key=<random>] password:] Password:
```

Ansible never recognizes this as "its" prompt, so it never sends the password,
and waits out the full timeout. A human reading the same text has no trouble
recognizing it's a password prompt — which is exactly why every *manual*
reproduction in this investigation appeared to work instantly: a person can
parse a wrapped prompt; a regex expecting an exact string cannot.

This is a known, confirmed upstream issue:
- [ansible/ansible#85837](https://github.com/ansible/ansible/issues/85837) —
  describes this exact incompatibility
- [trifectatechfoundation/sudo-rs#1461](https://github.com/trifectatechfoundation/sudo-rs/issues/1461)
  — confirms the wrapping behavior from the `sudo-rs` side, labeled `wontfix`
  (not expected to change upstream)

Ubuntu keeps the original, traditional C-based `sudo` installed alongside
`sudo-rs`, under the name **`sudo.ws`**.

**Confirmed with a direct manual test**:
```
ssh -tt ansible@<ip> 'sudo -k; sudo -S -p "EXACT-MARKER:" -u root id -u'
```
Returned `[sudo: EXACT-MARKER:] Password:` which is the wrapped prompt, byte for byte matching the bug report, visually confirming the diagnosis.

**Fix: force Ansible to use the legacy `sudo` binary instead of `sudo-rs`:**
```
ansible myhosts -i inventory.ini -b -m command -a "id -u" --ask-vault-pass --ask-become-pass -e ansible_become_exe=/usr/bin/sudo.ws
```
Returned `rc=0`, output `0` (root's UID) now works correctly, with
the password still protected by Vault, no weakening of the sudo policy.

**Permanent fix applied:** `ansible_become_exe: /usr/bin/sudo.ws` set in
`group_vars/myhosts/` (a plain, non-Vault file — this value isn't a secret),
so every future play against this host group uses the legacy `sudo` binary
without needing `-e` on every invocation.
